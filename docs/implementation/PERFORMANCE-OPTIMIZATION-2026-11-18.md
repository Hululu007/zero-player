# Zero Player 资源、耗电与流畅度专项评估及优化设计

版本：1.0 | 评估日期：2026-11-18 | 平台：Windows、Android 手机及 Android TV

评估对象：`K:/zero-player` 当前实际工作区。报告性质：源码评估、现有交付物量化、优化设计及验收计划。本轮未实施业务优化，未重新构建发行包。

## 1. 核心结论与实施建议

当前项目已有较完整的性能保护基础：数据库在后台执行、HTTP 有并发限制和播放优先级、媒体缓存有容量与引用保护、正文预读可取消、长章节分批排版、漫画按需加载，以及阅读和隐藏状态下的可选维护避让。优化应继续沿这些边界推进。

最值得先处理的是**一次业务变化引起的额外工作**。典型链路包括：音乐记录进度写入 `app_meta`，使已经访问但隐藏的直播页面重新查询、解码和排序频道；播放位置通知使整棵播放页面重复构建；播放历史和诊断快照按周期持续写入。它们有明确源码依据，适合在保持用户行为的前提下先消除放大，再进行复杂存储迁移或解码调参。[E02][E04][E05][E06]

建议首批选择以下五组，先建立计数和时序基线，再逐项对照验收：

1. 细化元数据通知与页面可见性：音乐进度不再使隐藏直播和首页执行无关加载。
2. 拆分播放器状态订阅：进度只更新进度区域，视频节点及页面结构保持稳定。
3. 合并无变化的进度写入，分离健康采样和诊断落盘：保留切换、暂停、退出和故障证据。
4. 音乐历史增量更新、歌词原生消息去重：避免每次记录重新读取所有歌单。
5. 建立跨模块资源预算及可观测性：先看见播放、下载、阅读、封面、探测同时发生时的总量，再调整并发。

内存的优先关注点是大图放大、PDF/EPUB 导入、长期保留的分支页面、整份元数据和字体常驻；包体的最大已量化机会是字体。已有 Android ARM64 测试 APK 为 **74.48 MiB**，三套字体的压缩体积合计 **39.59 MiB，占 APK 53.16%**。这说明字体分发策略值得设计，但包体缩小不能直接换算为运行内存或耗电同比下降。[E15][E19][E25]

**目前不能判断本项目实际耗电是否偏高，也不能承诺节电百分比。** 本轮没有连接 Android/TV 设备，未做真实媒体长时播放、Windows 性能采样或电池能耗测量。下文“收益”表示可消除的工作及待测方向；量化结论仅限本轮实际统计的源码和已有包体。

## 4. 通知、状态与数据库：先消除跨模块放大

### 4.1 已确认的放大链路

`MusicController` 约每 5 秒记录播放历史。`MusicLibrary.record` 写 `app_meta` 后，经 `_write` 再执行 `_read`，重新加载歌单及历史。历史有 200 条上限，歌单最多 100 个、每歌单最多 500 首，并非无限增长；但在较大用户库下，每次位置变化都可能触发与本次变化无关的 JSON 解码。[E06]

`LivePage` 监听的表集合包含整个 `app_meta`，收到变化后做 250 ms 合并加载。`LiveRepository.channels` 会读取频道、健康信息，解码并应用默认值和排序。因此访问过直播后，切到音乐，周期性音乐进度写入仍可能使隐藏直播分支重新加载。阅读进度和缓存元数据也可能触发相同链路。`StatefulShellRoute.indexedStack` 保留页面，不自动取消这些 Dart 订阅和数据库读取。[E02][E06][E07]

视频进度写入 history 后，已访问的发现页监听 history 并重新查询 `recentWorks`。此链路可能在页面不可见时继续。对用户而言只有位置变了，列表内容身份和顺序未必需要每次重建。[E04][E08]

这些事实不等于确认泄漏：页面和数据可能有界，问题是无关刷新次数及其 CPU、分配和 I/O，需通过计数器验证。

### 4.2 推荐设计：事务内归并，按域失效

短期保留现有数据库结构，为写操作提供明确变更域，例如 `music.history`、`music.playlists`、`books.progress`、`live.defaults`。可在当前 `changesFor` 旁增加 metadata key/revision 范围；SQL 无法明确推断时保留保守全量失效。新增接口名称属于设计提案，不是当前已有实现。

一次事务累计变更域，成功提交后发布一次；回滚不发布，嵌套事务沿用当前语义。重复写入相同值可在仓库层去重。不要把 SQL 正则扩展成复杂依赖推断器，也不要新增承载所有业务的万能事件总线。

读取方只监听其真正使用的域。隐藏页面将非安全的展示数据标为 dirty，恢复可见时按 revision 加载一次；在途旧查询用 generation 丢弃迟到结果。可见页面将连续变化合并，但不丢失最终状态。

**策略撤销、来源封禁和内容限制仍立即作用于播放、下载和准入。** 只能延迟隐藏页面的展示刷新，不能延迟业务安全状态。设置中改变监管规则后，即使页面隐藏、下载正在进行，也必须保留原有取消和重验行为。

中期把高频进度、音乐历史和阅读缓存索引从通用 `app_meta` 拆出，只在写放大、查询或迁移收益被量化后实施。当前数据库已使用 `NativeDatabase.createInBackground`，再次提出“把 SQLite 搬到 isolate”不能解决这里的主要问题。[E01]

### 4.3 验收与收益判断

- 已访问直播后隐藏，连续音乐播放 10 分钟：音乐历史仍按契约更新；单纯音乐进度引起的直播 `channels` 查询次数应为 0。
- 不可见发现页不因每次视频位置保存重复读取；返回时列表、续播位置、标题和标签正确。
- 单事务只发送一次对应失效，回滚不刷新；安全状态不经过可见性 debounce。
- 记录每次变更产生的 SQL 数、解码记录数、页面 build 次数和 allocated bytes。先以这些可控工作量证明冗余已消失，再判断 CPU/耗电收益。

## 5. 播放、音频与界面流畅度

### 5.1 视频状态订阅分层

`MediaKitEngine` 把约 8 类状态流按 50 ms 合并，事件密集时上限约 20 Hz，实际频率取决于原生事件，并不是每秒固定产生 20 次。`PlaybackController._onState` 处理后 `notifyListeners`，`PlayerPage` 的整页 `ListenableBuilder` 会重新构建 Scaffold、视频区域和控制区域。[E03][E04]

推荐将状态按使用者分开：

| 状态域 | 通知原则 | 主要订阅者 |
| --- | --- | --- |
| 内容/播放会话 | 作品、线路、集数或授权代次变化时立即发布 | 标题、选集、会话与策略处理 |
| 传输状态 | 播放/暂停、加载、错误、结束等语义变化立即发布 | 播放按钮、缓冲和错误面板 |
| 播放时钟 | 根据可见 UI 精度限频；拖动、seek 完成保留精度 | 进度条、时间文本、字幕/歌词所需部分 |
| 诊断/解码统计 | 诊断面板可见时订阅或低频汇总 | 开发工具、异常监测 |

让 Video/纹理节点和页面结构成为稳定 child，局部构建时钟与控制按钮。控制条隐藏时取消纯展示位置订阅，保留引擎和业务状态处理。只在确有绘制隔离收益处加 `RepaintBoundary`，不能遍布边界增加图层和显存。

不应对整个 `_onState` 统一加大 debounce；自动跳过、播放恢复、线路错误、seek、策略撤销可能依赖其时序。UI 更新限频与业务状态处理分开，既可减少 build，也便于测出真正的 raster 成本。

验收覆盖显示/隐藏控制条、拖动进度、倍速、切集、切线、全屏、PiP、字幕和 TV 焦点。记录 UI 与 raster 帧时；Flutter 掉帧与原生视频解码丢帧分别统计。

### 5.2 视频历史和听书进度写入

视频控制器每 4 秒调用相关策略检查与保存。非直播、非切换状态会执行历史保存，当前没有独立的“位置未变化”去重。因此暂停同一位置时仍可重复写入。历史保存还会先记忆内容，再执行历史 UPSERT。[E04]

推荐保留策略检查频率和授权语义，只将持久化分为：内存中的最新位置、dirty revision、单个待执行写任务和最后成功写入位置。同位置不写；正在写入时合并到最新 revision，避免异步任务重叠或旧结果覆盖新位置。

切集、切线、暂停、进入后台、正常关闭强制提交关键快照；异常杀进程仍可能丢失最后一个检查点，应明确目标，例如默认最多约 5 秒而非声称绝不丢进度。用户手动 seek 和未知时长历史沿用现有精确续播契约。存储失败不得清除 dirty 标记。

听书控制器约每 5 秒走 `saveBook`，有全书对象及目录序列化成本；它不同于文本阅读已使用的 SQL `json_set` 进度路径。短期先去重并提供专门进度写入口，中期共用按书籍身份的进度表，但不共享播放会话所有权。[E09][E14]

### 5.3 音乐、广播、悬浮歌词和 SSE

音乐已有约 250 ms 的 UI 节流，歌词换行可即时刷新。应保留这一交互优势，优先让历史在内存中增量更新；播放位置记录不重新读取所有歌单。歌单编辑、导入或外部修改才按相应 revision 刷新歌单数据。[E06]

悬浮歌词目前随控制器通知发送 MethodChannel payload，busy 只合并正在发送的任务，没有对 title/lyric/status 内容签名去重。Android 再次给 TextView 赋相同值可能带来布局/跨线程成本。可按实际显示内容比较，仅变更时调用；歌词换行、歌曲切换、可见性与播放状态立即发送，去重不能增加歌词延迟。[E10]

广播控制器可对不显示的位置事件做 distinct；听书仅通知实际展示字段变化。`BackgroundAudioGroup` 继续协调当前音频，避免每个普通位置事件导致所有下游重复处理。Windows 托盘已有 `_lastState` 去重，不能把它描述为每次通知都调用原生。[E09]

音乐接口 SSE 已限制最多 4 个订阅，20 秒心跳仅在有订阅者时存在。无需再次“修复无客户端心跳”。后续可评估按字段变化发送状态、慢客户端有界缓冲和主动断开；需要保留客户端重连的完整快照与兼容契约。[E11]

试听预检已有候选数、分组数和 TTL 限制。策略应围绕当前歌曲、下一首和近期实际使用候选，结合取消与缓存命中，避免为了“更快”预检整个列表。音频 engine 已使用 `videoOutput:false`，不能把关闭音频视频输出列为新收益。

## 6. 耗电相关的周期任务与诊断 I/O

### 6.1 诊断采样和落盘解耦

`PlaybackMonitor` 每 5 秒采样，Android 每 3 个 tick 读取一次额外原生快照。每次采样会持久化；suspended 主要跳过部分原生解码统计，仍保留 RSS/设备及快照流程。`PlaybackJournal` 用有序队列、临时文件、`flush:true` 和 rename 保存，两份快照有界，并不是无限日志。[E05]

按常数推算，每小时有约 720 次周期性快照机会、900 次视频保存触发，另有首尾和事件写入；这是源码频率推算，**不是本轮测得的磁盘写次数、fsync 次数或能耗**。

推荐三层设计：

1. 业务健康检测：保留及时发现卡顿、故障和策略异常所必需的采样，不与诊断文件周期绑定。
2. 内存诊断：使用按条数及字节双限额的环形缓冲，存最近状态及摘要；只在实际播放时采集需要的属性。
3. 持久快照：正常运行按较低频率合并保存，例如候选 30-60 秒；故障、切换、进入后台和退出写关键记录。异常前后保留上下文，不能以关闭诊断换取省电。

需要定义强制终态写入和未完成写任务的关闭次序，保留上次异常退出判断，避免降低落盘频率后把崩溃误判为正常退出。日志中的媒体 URL、请求头和监管信息按原有隐私约定处理，不能为性能埋点扩散敏感内容。

### 6.2 平台状态与可选维护

`ForegroundWorkload` 已让阅读及应用隐藏阻止部分可选源探测；视频播放本身未获得阅读 gate。源监控约每 30 分钟检查计划，书源首次约 30 秒、后续每 30 分钟最多检查 20 个来源；启用与停用来源的 due 周期不同。它们是应用进程内任务，不是已证实会在系统休眠中唤醒设备的 OS 常驻服务。[E02][E20]

推荐把可选维护统一到一个小型计划器：记录 due、jitter、最近失败退避和取消 token；阅读、首屏关键操作、播放启动、低电量或热状态时延后可选任务。恢复后按预算逐步运行，不把全部逾期任务集中补跑。

“统一”只负责许可和时机，各模块仍负责自身来源、凭据和业务状态。已存风险和入口即时检查继续生效；自动来源抽查可退让，不代表允许忽略监管更新。

对 timer 先计算有多少实际工作，不能只以定时器数量证明高耗电。没有音频播放、下载、诊断订阅和维护需求时，目标是让纯展示/预取任务可静止；实际耗电再由系统追踪确认。

## 7. 网络、下载与预取的总预算

### 7.1 当前限制与覆盖空隙

默认 `MediaHttpClient` 创建的 scheduler 是 globalLimit=20、playbackReserve=2；scheduler 类自身默认 8 不代表生产实例值。originLimit=2、backgroundLimit=4；HTTP 每 host 连接上限 4，idleTimeout 为 20 秒。播放优先只决定排队次序，不抢占已开始的流式响应。[E12]

书籍仓库还构造独立的 `MediaHttpClient`，host 连接上限 2，拥有独立 scheduler。因此现有“global”是单实例上限，不能视作应用总并发。封面有局部调度，并继续经过下游共享 HTTP；书籍下载并发按单书叠加，音乐另有独立队列。[E12][E13]

排队任务每次 drain 会排序，当前无统一最大排队容量。这说明应设计反压和取消，并不证明已经发生无界内存泄漏。现有 DocumentClient 带优先级传递、瞬时错误的一次重试和约 25 秒 active 网络预算，排队时间不当作网络超时，优化时保留其区别。

### 7.2 推荐设计：共享资源许可，保留业务隔离

先增加全应用观测：active/queued 按模块、优先级和 origin 分组；记录排队时长、取消/超时、实际字节和重试。再抽出轻量资源许可层，按网络请求、下载写入和 CPU 重任务分别限额，不建立一个涵盖所有任务的巨型调度器。

网络许可可包含：总 active、后台 active、每 origin、当前交互预留、metered 状态和热状态。独立客户端仍保留 HeaderPolicy、目标校验、来源租约和 cookies/认证隔离；不能为复用连接混用凭据，不能持有许可等待另一个许可形成死锁。

队列设置模块配额和总容量。超过配额时，对重复封面/预读可去重或取消最旧无消费者任务；用户下载需要展示等待状态并持久保留任务意图，不能静默丢弃。对不同 origin 使用公平轮转和退避，只有 profile 证明排序成本明显时再更换队列结构。

播放交互优先，但后台任务不能永远饥饿。测试同时包含持续搜索、封面加载和大文件 streaming；优先级不能回收已占用的网络连接，取消只能针对本任务合法持有的 lease。

### 7.3 下载写入与检查点

视频 MP4 约每 500 ms 更新 DB 进度，并按约 1 MiB `sink.flush`；这里的 Dart sink flush 不能简单等同操作系统 fsync。完成时还会完整计算摘要并验证。HLS 按分片提交进度，最终校验有完整性意义。[E13]

建议分离：UI 内存进度（候选 250-500 ms）、可恢复检查点（候选 2-5 秒或一定字节）、完成/暂停/取消的强制持久化。下载恢复必须从已确认的文件长度与校验状态出发，不能仅信任 UI 上的 downloaded 字段。只在重读验证有重复证据时合并流程，保留重启和外部篡改检测。

调度器目前读取全部任务，逐任务查询 pin，再循环调度，具有 N+1 和重复全扫机会。改为一次批量查询 pin/引用映射、活跃任务索引及增量状态队列；不牺牲删除原子性、取消与 pin 释放。数据库事务批处理要限制长度，避免占住写锁阻塞监管和当前阅读进度。

Android 隐藏时视频下载按当前实现暂停；书籍下载协调器是进程内任务，不能描述成系统保证的后台服务；音乐下载也有自己的串行及容量限制。优化前分别记录现有生命周期，再按原语义验收。

### 7.4 预取按收益调整

HLS 预取已有窗口 3、暂停时默认不工作、最大字节及串行 fetch；正文预读已有默认 2 章、0-5 可配、停留 700 ms、单路、默认非计费网络和后台取消。应保留这些限制。[E14][E18]

HLS 可按可播放秒数和字节双预算替代固定分片数，并结合当前缓冲、命中率、下一段下载耗时和最近 seek。正文仍优先当前章与下一章，离线正文命中不发正文请求。计费、低电或热状态先减少可选预取；不要擅改用户主动下载或默认画质。

衡量有效预取字节/总预取字节、实际使用等待时间、取消剩余工作及无线电尾部影响。缓存命中率高但内容从未被用户读取，仍可能是能耗浪费。共享 fetch 的生命周期独立，停止预取不能取消另一播放/下载消费者。

## 8. 缓存、I/O 和持久化结构

### 8.1 分片缓存算法

`SegmentStore.initialize` 读取全部索引，再逐项检查文件存在和长度；索引元数据常驻。容量 `cacheBytes` 通过遍历求和，腾挪空间时再次扫描；写文件后重新读取文件计算 SHA-256。大缓存下可能影响启动、每次提交和磁盘吞吐，具体拐点未测。[E17]

- 先维护 O(1) 已知字节计数，在提交、淘汰、恢复隔离、删除失败时保持一致；以实际文件验证校准，不以计数替代文件完整性。
- 对 LRU/可淘汰项维护轻量索引，避免每次排序全部条目。pin 与 ref 保持独立，删除失败进入已有延期清理路径。
- 启动恢复分批校验并记录阶段耗时；缓存被请求使用前仍确认其达到原有可信要求。对已引用离线资源不能先发布可用、稍后才发现损坏。
- 网络 chunk 同时送文件 sink 与 chunked hash，避免“刚写完立即再读一次”纯重复 I/O；完成后原子提交摘要。重启、离线验证和外部修改检查仍独立保留。

索引持久化若变化，先保证崩溃恢复和 schema 版本，不能只为降低启动耗时把坏行或未知文件删除。验收应覆盖 1千/1万/5万分片、满容量、删除受阻、并发 fetch、断点恢复和索引损坏。

### 8.2 阅读进度、正文与图片缓存

当前阅读进度已改为 SQL `json_set`，不再每次在 Dart 解码再编码整个目录。它仍更新大 JSON 行；新正文写入 `cacheReading` 时仍扫描缓存键与字节，图片及混合缓存也有相应扫描。图像 base64 写入 JSON 还增加文本体积及中间对象，base64 理论编码约为原字节 4/3，实际总开销更高且依场景而定。[E14][E15]

结构设计候选：

| 方案 | 优点 | 代价及适用条件 |
| --- | --- | --- |
| 维持结构，去重/批处理/字节计数 | 风险较小、可分批交付 | 不能消除大 JSON 行本身的写放大 |
| 进度独立表 | 高频小行写入、查询与通知明确 | 需要迁移、原子更新和回退；按书籍/章节身份绑定 |
| 正文索引 + 文件/Blob 内容 | 淘汰不扫大 JSON，图像无 base64 | 文件/DB 一致性、孤儿清理与内容验证更复杂 |
| 统一内容索引，业务预算独立 | 可共用校验与文件生命周期 | 复杂度最高；仅在多个模块重复实现被证实时考虑 |

优先实现“进度表 + 每类缓存索引”，不一次迁移全部书籍、音乐和媒体数据。索引至少记录身份、来源版本、字节、访问时间、校验/策略版本、pin/引用和提交状态；不能复用未绑定策略的“已检查”标志。

迁移读旧写新需有明确期限和 schema 依据，不增设永久兼容层。读取旧数据、迁移新数据、标记成功必须可以恢复；恢复失败不清空用户书架或离线文件。保持旧来源版本留存和章节来源契约。

### 8.3 数据库和长期内存

不要先把 SQLite 全部读出缓存。按使用场景建立有界缓存和 revision 失效，测量 SQL 条数、查询行数、JSON 解码字节、GC 与驻留量。对直播/EPG 的索引先运行实际查询计划和数据量基准，再决定组合索引；索引也会增加导入写成本。

备份、导入和清理是低频路径，适合在显式操作时做有界批处理或 worker。不能周期性无依据 VACUUM、清空 WAL、遍历全部目录或触发全局 GC，以免增加写放大和前台卡顿。维护行为要按实际数据库参数、空间和查询计划决定。

## 9. 阅读、文档、图像与字体

### 9.1 保留已完成的阅读优化

2026-11-17 的阅读专项已经实施：独立分钟时钟、后台取消、约 3 秒进度去重与退出保存、缓存命中免重写、超过 12000 字符按约 6 ms 分批排版、取消时释放 TextPainter、默认两章预读、阅读时可选源抽查避让、漫画宽度解码限制等。本轮将其作为现状，不再次列成未修复问题。[E14]

历史 Windows Debug 同步排版结果为：2850 字 9 ms、14250 字 35 ms、95000 字 226 ms、475000 字 1038 ms，分别对应固定字号、窗口和夹具。它说明总排版工作随文本规模增长，不是本轮实测，也不代表当前分批后的单帧或 Android 耗时。

### 9.2 长章节排版与翻页

6 ms 是一批工作的让出预算，不保证每帧在 6 ms 内完成；单次 TextPainter 工作、框架构建、栅格及 GC 会叠加。TextPainter 属于 UI 引擎资源，不能将现有排版原样丢进普通 Dart isolate。[E16]

可先建立按内容摘要、字体/字号/行距、实际视口、文字缩放和排版版本的有界页布局缓存，当前章节优先，取消旧任务并丢弃旧 generation。缓存结果要处理字体首次加载和窗口变更，不能只以章节 ID 命中。

更复杂的“当前可见页先完成，后续继续排版”需要定义总页数未定时的 UI、章节内锚点与跳转行为；否则可能改善首帧却破坏进度。先对 3千/1.5万/10万/47.5万字夹具测首次可用时间、总耗时、峰值内存与点击响应，再决定是否引入分页任务缓存。

自动滚动使用帧回调具有持续 CPU/GPU 成本；减少动画、静止阅读、手动翻页分别测量。尊重用户样式和系统减少动画设置，不把统一关纹理或动画当默认优化。

### 9.3 PDF/EPUB/本地书导入

本地文件上限约 128 MiB；TXT 全文读取后 worker 解析。PDF 导入用完整 bytes 打开并逐页取文本，页面数有 4000 上限；PDF 阅读显示已有 file/native 路径。EPUB 限总解压约 256 MiB、单 entry 16 MiB、约 4000 entry，并已在 worker 处理 ZIP；但整 ZIP、规范化文本、inline 图片以及重开阅读再次解析会带来峰值。[E19]

推荐“验证后的持久规范化索引”：以文件摘要、解析器版本、策略版本及来源身份为键，保存目录、章节文字/资源引用和已完成检查状态。重开优先复用经过重验的索引，按章加载正文和图片；更改内容策略后只复用允许复用的解析结果，重新执行必要内容判断。

能使用文件路径或分段 API 的地方避免额外整份 bytes 拷贝；是否支持由 pdfrx/底层接口和安全验证实际确认。worker 转移大二进制可评估 `TransferableTypedData`，只在减少拷贝被测量后采用。worker 不等于内存免费，多 isolate 可能同时驻留完整输入和输出。

导入完成前的授权和内容检查保持原顺序，不能先展示未校验正文再补检查。清理应在引用释放后处理规范化文件，保留原文件和失败诊断；超限样本仍明确拒绝。

### 9.4 大图、漫画与全局图片缓存

全局 Flutter ImageCache 设置为 120 项、64 MiB；这不包括所有 live image、原生解码缓存、纹理、GPU 表面或 PDF 内存，因此不是应用图片总内存上限。[E02]

漫画正常阅读已有按宽度解码，放大窗口仍使用不带 `cacheWidth` 的 `Image.memory`。24,000,000 像素上限对应单份 RGBA 约 **91.6 MiB**，还可能同时存在原始压缩 bytes、不同解码尺寸和 GPU 纹理。该值是像素公式估计，不是本轮观察到的峰值。[E15]

建议按设备能力与视口设解码像素预算，对超长图采用分片/平铺或区域解码，放大时按缩放级别请求更高分辨率。限制当前和少量相邻页，不预解码全部章节。缓存 key 区分尺寸但限制变体数量，关闭放大后释放专属引用，避免“低清+高清+上一页”同时无意常驻。

弱设备上可提供明确画质档位，保留用户放大能力，不静默截断正文。针对动图、长图、连续快速翻页、缩放和反复打开关闭，测 Dart heap、native/PSS、GPU 和回落曲线。无法平铺的格式应明确上限和错误处理。

### 9.5 字体和原生枚举

阅读字体已有固定版本、大小/SHA-256/OFL 校验和按需下载。Flutter 当前没有通用卸载已加载字体的 API，删除磁盘字体不保证本进程内存立即释放。不能通过反复加载/清除来“回收内存”。[E14][E26]

Android XML/Windows DirectWrite 的系统字体枚举经方法通道同步执行，适合在原生工作线程处理并缓存一次会话结果，UI 只接受最终列表；避免每次打开字体选择器重新枚举。字体列表懒构建与加载状态要能取消/关闭，但已开始的 Flutter 字体注册按真实 API 能力处理。

## 10. 搜索、发现、来源与直播

### 10.1 大结果集与列表

视频搜索已有约 120 ms 通知合并和 groups 缓存；并发初值及设置可能不同，不能把所有实际请求都固定描述为 6。首页 SliverGrid.builder 和自动加载数量限制已存在，直播频道列表也是懒构建，优化重点不是笼统“改成 builder”。[E08][E21]

可预计算搜索排序分值，避免比较器每比较一次就正则分析；对书籍搜索和直播筛选建立按 query/结果 revision 的分组排序缓存，只有输入或数据实际变化才重算。大量结果按增量批次提交，保留稳定 identity、选中状态、键盘/遥控焦点和无障碍顺序。

有条件地把纯文本标准化、解析和排序送 worker，前提是 profile 显示 UI 被这些任务占用，并验证传输成本低于收益。小列表留在当前路径，避免每次按键创建 isolate。Document 的 text/json getter 热点可在单响应生命周期缓存解码，但不应到处扩大数据保留时间。[E12]

封面沿用现有懒加载和并发限制，按显示宽度解码，检查 URL/尺寸变体重复下载和失败重试。不要无限增加 ImageCache 来掩盖滚动抖动。

### 10.2 直播和 EPG

直播先修元数据误触发和隐藏页面加载，再评估筛选时的全量 filter/map/group/sort。对大频道库可维护规范化检索字段及分组索引；输入 debounce 应保持 TV 按键响应和搜索完成的最后一次结果。[E07][E22]

EPG 已使用事件式 worker 解析、约 20 MiB 解压 body 上限、1万频道/10万节目及前1后7日窗口，并按约500条批量事务。不能将其描述为主线程 DOM 解析或无事务逐条插入。[E23]

后续候选是条件请求/guide TTL、稳定数据的增量替换、按批传递解析结果以减少大 List 跨 isolate 峰值，以及对 source/channel/start 等实际查询做 EXPLAIN 后建立适当组合索引。只有服务端和缓存头允许时才跳过重新下载；频道删除、时区、节目修订和坏行隔离保持正确。

### 10.3 来源与订阅

订阅刷新在首屏后启动，可能与源健康检查、书源检查、海报和用户搜索竞争。将其纳入可选维护许可，使用 TTL/jitter/退避，保留用户手动探测的独立交互优先级。来源导入、网页脚本线索、策略证据计算可能 CPU 密集，但只对独立纯函数和较大批次使用 worker，仍由仓库完成最终授权与事务提交。[E20]

不为性能把旧来源版本自动回收，也不扩大书源探测范围。来源失效、风险限制和用户手动刷新必须在 UI 中保持清楚，不能将所有失败延迟成无法解释的等待。

## 11. 内容过滤、AI 与导出

### 11.1 现有成本路径

普通后台内容特征管线使用按 visual/audio 需要工作的 `ProbeSampler`，不是始终执行全量转码的 FFmpegSliceSampler。采样使用单线程 FFmpeg、音频 16 kHz 单声道及约640像素图像；OCR 约2线程，ASR/keyword 约1线程。后台窗口约4秒、重叠0.5秒、领先12秒，完成或已领先时仍约400 ms 检查推进。[E24]

开销可能来自窗口间重复解码、每窗口外部进程/临时文件/worker IPC、模型首次加载与多个模块同时使用 CPU。实际哪部分占主导需用 timeline、进程追踪和真实媒体确认，不能把可选功能开销算成所有用户的基础功耗。

### 11.2 优化设计与限制

- 用播放位置/缓冲推进事件驱动下一窗口，空闲时避免高频无工作检查；保留 seek、速度改变、暂停恢复和取消的及时性。
- 合并确有重叠的解码工作，评估内存管道替代中间文件；设置样本字节、队列和并行上限，避免用无限缓存换临时 I/O。
- 按能力复用模型/worker，限制驻留数量、闲置释放时机和重新加载成本；复用必须隔离会话、来源和策略代次。
- 对用户可选增强功能按热状态、低电与前台优先级降低采样或延后；监管要求的过滤按既有安全语义工作，资源不足走已有明确失败/限制路径。
- 为效果保留固定标注样本、窗口边界、音画同步、seek 后覆盖范围和误判率门槛，不只考核吞吐。

若启用可选过滤导致明显软件解码竞争，可提供可解释的模式选择和能力提示。不能自动关闭成人过滤，不能跳过原生安全属性或放宽网络协议来提高命中率。

### 11.3 导出、备份和低频操作

FFmpeg 导出与播放/阅读争用 CPU 和磁盘，宜独立许可、取消和进度合并；线程上限按机器和前台工作负载测试，不能一律开满核心。输出临时文件、完整校验、授权前后复查及失败清理保持原子性。

备份已有约20 MiB、每表2万条等限制，JSON 编解码和校验可按规模 worker 化；低频操作优先展示进度和取消，避免长时间 UI 阻塞。监管密码使用 Argon2id，约19 MiB、2 passes、1 lane，已运行于 isolate；不能为省 CPU 降低密码参数。[E27]

## 12. 平台、解码与生命周期

### 12.1 硬件解码需要观察，不宜先强改

视频成本通常还受编解码格式、分辨率、帧率、码率、色深、HDR/色调映射、字幕、输出驱动和实际硬解支持影响。现有引擎有约8 MiB缓冲和受约束的原生属性，单一参数不足以决定总内存。[E03]

建立硬解实际生效的诊断：记录请求设置、实际 decoder/输出、软件回退原因、解码/渲染丢帧、buffer underrun、CPU/GPU、热降频。对 H.264/HEVC/AV1、1080p/4K、SDR/HDR、字幕和倍速分别比较；只在设备支持和原生安全属性保持一致时评估设置。

不要直接启用任意 mpv/FFmpeg 选项、替换系统 DLL 或移除正确性检查。缓冲扩大可减少弱网卡顿，也会增加内存和无效预下载；缩小可减少内存，但可能增加唤醒和重缓冲，应按 buffer duration 和真实码率决定。

### 12.2 生命周期矩阵

| 状态 | 应保留 | 可暂停/降低的工作 |
| --- | --- | --- |
| 可见视频播放 | 解码、声音、业务状态、安全处理 | 可选维护、隐藏诊断面板高频 UI |
| PiP | 用户选定的视频及必要控制 | 主页面纯展示、非关键预取按策略 |
| 音乐/广播/听书后台 | 当前平台契约内的音频与控制 | 不可见歌词页面布局、无变化原生消息 |
| 静止阅读 | 内容展示、安全边界和必要交互 | 来源维护、无需求自动动画、过量预读 |
| Windows 隐藏到托盘 | 用户主动音频及退出/恢复控制 | 隐藏页面展示刷新、纯装饰动画 |
| 无任务且应用隐藏 | 恢复和安全状态 | 非必要 UI、预取、可选扫描 |

当前 Android manifest 未提供保证长期后台音频的完整 foreground service/MediaSession 集成，因此不能承诺系统杀进程后继续播放。如果未来要求可靠后台音频，应作为单独功能设计，评估服务、通知、音频焦点和系统限制；不能用永久 wake lock 或拉高进程优先级宣称省电。

视频当前后台挂起部分健康统计不等于自动暂停播放器。需区分 PiP、音频用户意图、进程可见性和平台回调，不能仅凭 `paused` 生命周期无条件停止。Windows 原生窗口隐藏、关闭重试、托盘退出与资源销毁需要真实原生测试，Dart fake engine 不能代替。

### 12.3 启动和内存压力

AppServices 当前串行加载监管/LAN/设置、内置视频源、sources、内置直播、分片索引、平台、托盘/音频组、网关和下载恢复。传参构造 `BackgroundAudioGroup` 时会求值音乐/广播/听书控制器，听书进一步触发书籍仓库；不代表这时已经创建三套原生 mpv，engine 本身仍有懒创建。[E02]

推荐阶段：

1. 必须安全完成的监管、配置及网络边界；此阶段失败仍按现有失败页阻断。
2. 首屏需要的数据和路由；记录 first frame 与真正可交互两个时点。
3. 用户进入模块时按需构造非必需仓库/控制器，后台恢复任务按契约需要启动。
4. 缓存校验、订阅和可选维护按预算分批进行；播放首次 open 仍等待其所需组件达到可信状态。

不要为了首屏指标把全部工作简单推到首帧后一瞬间。需要测首屏之后30秒的 CPU、IO 与首次进入各模块延迟，并分别处理文件启动入口、下载恢复和后台音频恢复。

对未使用分支可在内存压力下释放可重建的页面数据/封面引用，保留导航、滚动位置和当前会话；若设计 route eviction，先验证 TV 焦点、未保存表单及原生纹理生命周期。不要无条件销毁所有分支来换低 RSS。

## 14. 统一资源策略及候选参数

资源策略只做显式许可和建议，不应变成控制所有模块的“总上帝对象”。模块保有任务状态，许可层只知道资源类型、优先级、成本估计、取消和生命周期；先实现最小网络/重任务预算，再根据证据增加能力。

输入信号建议为：应用/路由可见性、当前播放/阅读、网络是否计费、设备档位、低电/热状态、用户选择。热状态回落使用滞回，防止频繁切档；系统接口不可用时采用稳定默认值。用户主动下载、音量和画质不被静默改写。

## 17. 测量方法、指标和建议门槛

### 17.1 构建与实验控制

帧时分析使用可追踪的 profile 构建，能耗/用户体验最终用同配置 Release 复验。Debug 只用于定位和功能回归。设备A/B使用相同编译模式、依赖、媒体、亮度、刷新率、音量、网络、电量范围和温度，轮换版本顺序。

每场景预热约2分钟、稳态至少10-15分钟、至少3次成对重复；冷启动单独多次测量并明确磁盘/字体/媒体缓存状态。长时内存/可靠性至少30分钟和120分钟两个窗口。实验时间是建议，不是本轮已经执行。

Android电池测量建议拔线或使用明确电源仪，避免USB充电改变温度和电流；无线ADB也有开销，应保持两版一致。电量百分比整数不足以评估短时节电。电流符号、µA/mA和电压单位按设备核实，能耗积分及系统估算分别标记。

### 17.2 指标定义

| 维度 | 记录项 | 正确解释 |
| --- | --- | --- |
| 首屏/启动 | 进程启动、首帧、首可交互、模块首次进入 | 区分冷/热、文件启动、恢复任务和后置工作 |
| 交互 | 输入到反馈、页切换、seek/切章/搜索结果 | p50/p95/p99及错误率，不能只看平均 |
| Flutter渲染 | UI/raster时长、超预算帧数、长帧分布 | 60/90/120Hz预算分别16.67/11.11/8.33ms |
| 视频体验 | 首画面、重缓冲时长/次数、native丢帧 | 分离网络、解码、渲染和Flutter UI |
| CPU/线程 | 每进程CPU时间、线程、唤醒、上下文切换 | 说明100%是一核还是全机归一，不跨设备直接比 |
| 内存 | Dart heap/GC、RSS/PSS、native/GPU、峰值/回落 | PSS/RSS为不同口径，不能直接叠加到总内存 |
| I/O | 写/读字节、文件替换、DB语句/页写、flush | 请求计数不等于物理磁盘写或fsync次数 |
| 网络 | 请求/字节、重试、排队、命中/有效预取 | 区分正文/封面、用户下载/可选任务 |

| 正确性 | 恢复位置、终态、授权、摘要和任务一致性 | 性能改善不能抵消功能或安全回退 |

首轮建议门槛应在阶段A后确认：

- 基本交互在目标刷新率下分别评估UI/raster p95与p99，活跃动画/滚动超预算帧比例候选≤1%；报告最差场景，不把静止无帧平均稀释卡顿。
- 本地普通操作输入反馈 p95 候选≤100 ms；网络首画面和搜索不能用一个固定门槛混盖，使用受控网络延迟及缓存条件对照。
- 隐藏直播受音乐进度影响的无关查询为0、暂停同位置的重复历史写为0、相同歌词payload原生消息为0，作为确定性回归门槛。
- 30/120分钟经过稳定周期后不出现随次数持续上升的不可回落内存；应分析斜率、循环后回落和原生对象数，不能只要求RSS完全回到启动值。
- 能耗的接受条件为收益超过设备重复测量噪声且主要体验不退化。若3次结果置信不足，增加样本并报告无定论，不给虚构省电比例。
- 所有迁移、取消、异常退出、监管撤销和缓存完整性回归保持通过；性能样本不得出现新的崩溃、重复播放、音画错位或后台失控。

上述百分比与时间是**建议目标**，不是对当前项目的实测评价或本轮承诺。

### 17.3 Android / TV 工具

使用 Perfetto/Android Studio System Trace 观察调度、FrameTimeline、CPU频率/idle、I/O、音视频与系统热状态；FrameTimeline及GPU计数可用性依设备版本。Flutter DevTools记录UI/raster、CPU样本和Dart内存；`dumpsys meminfo`补充PSS/native。

使用WPR/WPA/ETW分析进程与线程CPU、文件/磁盘I/O、GPU和DWM，结合Flutter DevTools、Process Explorer等观察Dart/native与播放器子进程。分别测试窗口可见、最小化、托盘、全屏及多显示器/缩放。

## 20. 不推荐的优化路径与决策边界

1. 不以禁用监管/内容校验、减少密码强度、放松原生安全选项作为性能方案。
2. 不统一降低所有引擎事件频率，避免seek、恢复、跳过、歌词和错误状态延迟。
3. 不把所有解析和排版迁入isolate；先区分UI引擎资源、输入大小、拷贝和worker驻留。
4. 不靠无限增加连接、缓存或预加载换“流畅”；测混合场景与有效命中。
5. 不全局清理Pub/Gradle/Docker/业务缓存，不替换系统任意DLL，也不擅自删除用户字体和旧来源版本。
6. 不盲目重写播放器或升级全部依赖；以具体瓶颈、平台兼容及固定摘要为依据。
7. 不把包体、测试通过、CPU时间和Windows Debug数字换算成Android省电百分比。
8. 不把固定RSS不回启动值直接判断为泄漏；结合有界缓存、循环斜率、引用和原生对象证据。

真正需要在实施时确认的产品取舍集中在：字体是否必须全部离线、进度异常恢复窗口、低电模式是否减少预读、弱设备大图清晰度/放大行为，以及是否新增可靠后台音频。现有报告和首批无行为变更的消冗余工作不依赖这些取舍。
