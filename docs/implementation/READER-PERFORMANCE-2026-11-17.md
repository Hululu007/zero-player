# 阅读器性能与耗电分析

本轮范围：Windows、Android／TV 的网络小说、TXT、图文章节和漫画；EPUB／PDF 共用字体与安全区设置，保留原格式内容检查。当前进度仍以 [STATUS.md](STATUS.md) 为准。

## 结论与证据边界

已经修复缓存命中仍写盘、整页时钟刷新、滚动进度高频计时器、长章节连续占用界面线程、阅读时竞争的可选源抽查和无订阅者音乐心跳。下载、播放、即时内容／来源校验继续运行。

Windows 原生测试确认系统字体枚举、已校验开源字体实际加载、进度节流及退出保存、漫画交互。**没有连接 Android／TV 真机，未测得电流、能耗或续航提升百分比。** 不能把单元测试、Windows CPU 时间或 APK 构建成功换算成手机省电比例。

字体上游样本已取得并核对固定版本、字节数、SHA-256 与 OFL 许可证，离线原生加载成功；本机应用内真实在线下载复测超时（`.dart_tool/native-4e855b1d/reader_upgrade_native_test.log`），直接访问同一 GitHub Raw 地址也在 15 秒内未取得响应。本轮不能宣称当前网络下在线下载已经通过；下载失败显示可重试提示，已缓存字体仍可离线使用。

## 资源与耗电路径

| 路径 | 原有问题／成本 | 本轮处理 | 仍然存在的成本或边界 |
| --- | --- | --- | --- |
| 静止阅读 | 每分钟 `setState` 重建阅读页面 | 分钟时钟独立 `ValueNotifier`，只重建页脚时间；关闭时间显示／进入后台取消时钟 | 系统屏幕、显示刷新率与亮度通常是静止阅读主要能耗，尚未量测 |
| 滚动／翻页进度 | 每次移动取消并创建 550 ms 计时器；连续滚动可能一直不落盘 | 单个待执行计时器，最多每 3 秒保存；切章、后台、退出及时保存；相同位置不重复写 | 异常杀进程可能丢失最后约 3 秒进度；离开时异步存储不能抵御立即断电 |
| 长目录持久化 | 每次进度保存都在 Dart 读取／解码／编码整份目录 JSON | SQL `json_set` 更新位置与时间，保留收藏、追更和目录；4000 章目录回归通过 | SQLite 仍更新该行内容；要消除大行写放大需独立进度表与迁移，暂未引入 |
| 正文缓存命中 | 读取后再次 `cacheReading`，扫描缓存并淘汰 | 仅网络新取得正文写缓存；离线正文优先，缓存命中免重复写入 | 新增章节仍扫描缓存键和字节数；受 24 MiB 容量限制，未改动缓存表结构 |
| 长章节排版 | 完整 `TextPainter` 分页一次占用 UI isolate | 超过 12000 字符后按约 6 ms 预算分批让出事件循环，切换内容／字号／窗口后取消旧任务 | 总排版量未减少；单页排版本身可能超过预算，6 ms 不是帧时长保证；完成前显示排版状态 |
| 内容检查 | 普通正文在多个校验点重复编码／计算 SHA-256 | 只有命中复核标记时计算绑定原文与结果的摘要；无监管时免生成监管规范化文本 | 成人过滤与策略复查保留；未用不含策略版本的结果缓存跳过过滤 |
| 在线章节预加载 | 没有阅读会话预加载 | 默认后续 2 章、可设 0–5；停留 700 ms 后单路后台优先级请求；切章／退后台取消；默认非计费网络 | 缓存未命中时仍有网络与解析成本；不为预加载搜索备用来源，失败不提示、不自行循环重试；共享 HTTP 层原有瞬时错误重试仍保留 |
| 预加载调度 | 网络请求与当前章竞争连接 | 异步区域携带后台优先级，GET／POST 都传入原有有界调度器；当前章仍交互优先 | 已开始的网络传输不能靠优先级抢占，切章主动取消；真实站点限速待验 |
| 图片解码 | 漫画大图解码／缩放消耗内存与 GPU | 保留逐图懒加载、取消、像素限制及屏幕宽度解码上限；缓存图片片段列表，免每次创建列表 | 放大窗口仍需完整分辨率解码，超长漫画／动图须真机评估 |
| 手势冲突 | 中心点击直接打开图片；长图坐标与翻页窗口不一致 | 点击窗口两侧翻页、中央菜单；长按图片单独放大，关闭后返回；分页／滚动互不抢占点击与长按 | 漫画仿真仍映射横向分页，不模拟纸张；未改读屏手势系统约定 |
| 后台维护 | 阅读／应用隐藏时仍能启动定时源检测 | 阅读租约与前台状态共同阻止可选网页抽查和源可用性探测，并取消正在进行的自动探测 | 定时器本身仍每 30 分钟醒来检查一次；退出阅读沿用原计划，不集中补跑；已存风险与阅读入口校验持续生效 |
| 其他模块 | 音乐状态接口启动后无订阅者也有 20 秒心跳 | 首个订阅者出现才启动心跳，最后一个离开取消 | 实际音乐播放、歌词、下载继续工作，不强制暂停用户正在使用的功能 |
| 自动阅读 | 样式面板可能使翻页／滚动自动任务继续等待 | 打开样式时停止任务，只有先前在运行或本次新启用时恢复；退后台停止 | 自动滚动仍使用帧回调，平滑度以持续 CPU／GPU 活动为代价；无自动阅读时不启动 ticker |
| 字体 | 大 CJK 字体文件下载、校验和字体引擎常驻 | 按需下载固定版本，字节数与 SHA-256 校验，保留 OFL；本机缓存复用；系统字体按需枚举，列表按需构建 | 两款字体约 15.7／23.4 MiB；首次加载会占用 CPU／内存，Flutter 无卸载字体接口，删除磁盘副本后内存至本次运行结束释放 |
| 纸纹／动画 | 纹理与仿真翻页可能增加栅格工作 | 保留背景 `RepaintBoundary`、`shouldRepaint`；正文独立重绘；尊重系统减少动画 | 没有依据就不强行关闭用户纹理；纸纹／动画的真实 GPU 成本待设备测量 |

## Windows 原生排版基准

运行 `tool/run_windows_native.ps1`，Flutter Windows Debug，固定 346×710 逻辑像素、字号 21、行距 1.8、内置宋体，同一长章节中文夹具；日志 `.dart_tool/native-e867a5e1/reader_upgrade_native_test.log`。以下为同步排版辅助方法，验证完整分页结果连接后与输入逐字相同，用于估计总工作量。

| 字符数 | 页数 | 单次总耗时 |
| ---: | ---: | ---: |
| 2850 | 17 | 9 ms |
| 14250 | 84 | 35 ms |
| 95000 | 556 | 226 ms |
| 475000 | 2778 | 1038 ms |

该结果表明长章节一次完成会明显阻塞界面，因此阅读器采用同算法分批执行。分批的目的为提高输入响应性，不宣称降低总 CPU 时间。取消任务时让分页迭代器正常退出，以执行 `TextPainter.dispose`，不依赖垃圾回收释放原生排版资源。普通 3000 字章节保持直接排版，避免引入多余加载闪动。自动测试覆盖长章节排版中切换到新章节、返回已经完成排版的旧章节、重新进入取消章节，防止旧任务覆盖或滞留；不以纯空输出作为性能证据。

## 推荐测量矩阵

两版应用在同一设备上对照；固定屏幕亮度、刷新率、字号、纸色、温度、网络、章节和下载任务。每场景先预热 2 分钟，再采样至少 10 分钟，重复 3 次，轮换版本顺序。保持相同电池电量范围；充电会影响电流与温度，真机电池能耗测量应拔线，使用无线 ADB 或独立电源仪。

| 场景 | 主要观察 |
| --- | --- |
| 静止离线阅读，状态栏开／关，亮／暗纸色 | CPU 唤醒、屏幕亮度／面板差异；OLED 暗色与 LCD 不可混为一谈 |
| 手动每 5 秒翻一页／连续滚动 | 帧时、栅格线程、进度写入数和 I/O；验证最终恢复位置 |
| 自动翻页／自动滚动 | ticker CPU、掉帧与平均电流，分别测量，不用一个数字概括 |
| 在线首次阅读、关闭预加载／预加载 2 或 5 章 | 请求次数、下载字节、无线电尾部能耗、下一章首次显示耗时 |
| 已缓存章节与同章离线下载 | 必须无正文网络请求，离线正文覆盖缓存；不据封面请求误判正文缓存失效 |
| 阅读同时下载小说／漫画／音频 | 下载不中断；测当前阅读帧时与吞吐，保留原有并发上限 |
| 超长章节、4000 章目录、图片密集章节 | 首次排版耗时、峰值 RSS、解码内存、切章取消；不只测稳态平均值 |
| 切后台 10 分钟再回来 | 预加载取消、自动阅读停止；下载／播放按原语义持续；无重复定时任务 |
| 刘海、居中打孔、横屏、2 倍系统字号／键盘 | 第一行不被遮挡，留白增加后页码重排、进度稳定，设置可滚动 |
| Android TV 遥控器与 Windows 键盘 | 方向键／PageUp／PageDown／菜单、图片放大关闭、焦点恢复 |

## 只读采样工具

新增 `tool/capture_reading_power.ps1`，只读采样，不清空 batterystats，不修改亮度／刷新率／省电状态。脚本每次等待最多 60 秒，采集前后电池统计与帧时快照，以及电池、CPU、内存和温度的时间序列，写入 `build/reading-power/`。

```powershell
./tool/capture_reading_power.ps1 -Serial <设备序列号> `
  -Scenario reading-offline-static -DurationSeconds 600 -IntervalSeconds 30
```

`capture.json` 记录采样时间与场景。必须结合 UID 的 batterystats 差值、设备支持的 charge counter／功耗轨和 Perfetto 的 CPU／调度／FrameTimeline 轨迹；单次 `dumpsys cpuinfo` 或整数电量百分比不是能耗证据。`gfxinfo` 对 Flutter 自绘表面的覆盖有限，Flutter DevTools／Perfetto 帧轨是判断 UI／raster 抖动的补充。工具已通过 PowerShell 语法检查；无设备时不能声称完成硬件采样。

Windows 可用 WPR／WPA 的 CPU sampling、GPU activity、Disk I/O，结合 Flutter DevTools 的 UI／raster 帧和内存。RAPL／整机功耗只适用于可用的测量设备，不能替代 Android 结论。

## 验证与后续

测试与构建结果见 [STATUS.md](STATUS.md)。正常阅读净化始终在原文校验后执行，结果再校验；敏感替换只应用一次，摘要例外仍绑定精确文本，离线／下载证据和访问策略未放宽。缓存容量统计、独立进度表、OEM 字体可见性和设备刷新率策略属于后续以实测为依据的优化项，不能据本轮代码分析宣称全面消除耗电。
